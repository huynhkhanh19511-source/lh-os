# Role Cognition Model — Reality → Structure → System → Runtime

## Purpose

Defines Junior, Senior, and Architect as cognitive positions within Architectural Sensemaking, not necessarily organizational roles or career titles.

The model describes how one practitioner moves through Reality toward System formation and then returns to Reality through Runtime feedback.

## Core Model

**Reality → Recognition → Structure → System → Runtime → Reality Feedback**

### 1. Junior — Reality Recognition

**Primary question:** “Đây là gì?”

Cognitive operation:
- identify what exists
- establish context
- distinguish facts from assumptions
- avoid premature abstraction

Junior is the position of entering and recognizing Reality.

### 2. Senior — Structural Understanding

**Primary question:** “Nó vận hành như thế nào?”

Cognitive operation:
- identify patterns
- identify relationships
- identify dependencies and constraints
- understand causal and operational structure

Senior is the position of understanding how Reality is structured and behaves.

### 3. Architect — System Formation

**Primary question:** “Ta tổ chức nó thành System như thế nào?”

Cognitive operation:
- define boundaries
- compose components
- define interfaces
- establish principles
- evaluate trade-offs
- design system behavior

Architect is the position of forming a System from structural understanding.

## Runtime Is Not a Fourth Role

Runtime is the validation boundary.

The Architect's design enters Reality through Runtime, producing evidence that can confirm, invalidate, or modify the architecture.

**System → Runtime → Reality Feedback**

This prevents Architecture from becoming a closed theoretical loop.

## Cognitive Transition

```text
Reality
   ↓
Junior Position

   ↓

   ↓
System

   ↓

   ↓

   └──────────────→ revised understanding
```

## Important Principle

> Junior, Senior, and Architect are not necessarily organizational roles. They are cognitive positions a practitioner occupies while moving through Reality.

A single practitioner can move between these positions repeatedly within the same problem.

## Relation to Structure Artifact Patterns

Artifacts should be mapped to the cognitive operation being performed, not rigidly to a job level.

| Cognitive operation | Primary question | Typical structure artifact |
|---|---|---|
| Reality Recognition | What is this? | Concept Map / Mind Map |
| Structural Understanding | How does it work? | Flowchart / Causal Map |
| System Formation | How should it be organized? | System Map / Decision Tree |
| Runtime Validation | Does it actually work? | Test / Evidence Artifact |

This mapping is directional, not exclusive. An Architect can use a Flowchart; a Junior can produce a System Map. The distinction is why the artifact is being used.
